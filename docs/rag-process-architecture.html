RAG Workbench process architecture

Retrieval-first LangGraph workflow · data, models and governance

01 / Data

  • SEC EDGAR filing text is parsed, structure-chunked and embedded with Qwen3-Embedding into edgar_embeddings (chunk text, metadata and embedding column).
  • SEC companyfacts XBRL facts are extracted into xbrl_facts and read by the numeric Extraction step.
  • polygon_tickers company metadata and polygon_bars daily close and volume are read directly, not chunked or embedded.
  • ticker_embeddings holds ticker-profile vectors used only by the legacy /api/chat/rag route; neither embeddings table has a vector index.

02 / Retrieval and branching

  • Retrieval is the LangGraph entry node: BM25 + vector search over edgar_embeddings, RRF fusion, then on the hybrid path a candidate top-k (3 general, 2 latest, 8 comparison) and a cross-encoder rerank to at most 5, so at most min(top-k, 5) chunks survive; a relevance filter then drops irrelevant ones. If hybrid retrieval fails or returns nothing, a keyword fallback takes up to 5 filing-section chunks, reranks and relevance-filters them without applying the intent top-k.
  • The classifier then routes numeric questions through XBRL eval, Polars math and verification to output or abstention, and qualitative questions to an LLM answer with tool calling.

03 / Governance

  • Output, abstention and qualitative answers all pass through build_lineage: audit trail for every run, review queue on sampled or escalated routes, then human review and calibration. audit_runs and the review queue live in a separate review_queue.duckdb file (REVIEW_DB_PATH).
  • Abstention fires when verification returns FAIL or ERROR and returns a fixed message. Graph RAG is a separate /api/chat/graph-rag workflow whose Query graph step reads graph_triples. DeepSeek and MiMo answer; Qwen3-Embedding and the cross-encoder support retrieval.
